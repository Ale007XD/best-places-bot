# Best Places Bot

Telegram-бот: топ-3 кафе, ресторана и бара рядом с пользователем.

**Диалог:** геопозиция → один экран параметров (радиус + минимальный рейтинг +
«Искать») → одно сообщение с тремя местами. Под каждым: 🗺 карта · 📤 поделиться · 👍/👎 «был здесь» · 🚫 «закрыто».
Язык определяется автоматически (по языку Telegram), параметры запоминаются.

Стек: Python 3.11, aiogram 3.x, httpx, Redis, pydantic-settings, Docker Compose.

---

## Быстрый запуск

```bash
cp .env.example .env      # заполнить BOT_TOKEN и FSQ_API_KEY (+ GEOAPIFY_API_KEY для базового слоя)
docker compose up -d --build
docker compose logs -f telegram-bot
```

Обязательные переменные — только `BOT_TOKEN` и `FSQ_API_KEY` (Service Key из
Foursquare Developer Console). Базовый слой (места без рейтингов) работает на Geoapify, поэтому
`GEOAPIFY_API_KEY` стоит задать тоже: без него этот провайдер пропускается. Остальное
опционально, см. `.env.example`.

Проверка ключа Foursquare одной командой:

```bash
curl -s "https://places-api.foursquare.com/places/search?ll=10.7769,106.7009&radius=500&limit=1&fsq_category_ids=63be6904847c3692a84b9bb5" \
  -H "Authorization: Bearer $FSQ_API_KEY" -H "X-Places-Api-Version: 2025-06-17"
```

Команды бота: `/start`, `/me`, `/buy`, `/language`, `/paysupport`, `/terms`.
Админ (`ADMIN_ID`): `/money` (монетизация, лимиты), `/diag` (проверка сервисов), `/layout` (вид выдачи),
`/stats`, `/feedback`, `/refund <charge_id>`.

### Поиск

1. **Провайдер.** Один запрос обслуживается ОДНИМ провайдером (источники не смешиваются): первый
   по порядку, давший ≥ 3 *именованных* места, иначе тот, у кого мест больше; Mapbox —
   только если пусто у всех. Платный (рейтинговый) поиск идёт в Foursquare первым; базовый —
   по `BASE_PROVIDERS` (`geoapify,fsq,overpass`). Подробности — «Источники данных».
2. **Чистка до подсчёта провайдера** (чтобы мёртвые места не «засчитывались»):
   закрытые (`date_closed` у Foursquare; места, на которые пожаловались — см. «Закрытые места»),
   «битые пины» (≥ 2 места в одной точке с разными улицами; расхождение расстояния провайдера и
   расстояния по координатам > 150 м), нецелевые заведения (`venue_filter`: фитнес, отели,
   клиники и т. п. по названию и тегам OSM/категориям Geoapify; чекины и эмодзи-спам Foursquare;
   точки FSQ без адреса и рейтинга не засчитываются в порог «≥ 3 места» и ставятся в конец), а места, чей регион в адресе не совпадает с регионом точки
   поиска (Geoapify reverse), не удаляются, а уходят в конец выдачи.
3. **Дедупликация.** То же имя — дубль, только если ближе 40 м; похожее имя («Тосты» /
   «Тосты, винное бистро») — ближе 45 м; до 120 м — только при той же улице или если у одного из
   мест адреса нет (разные известные улицы — разные заведения), ядро имени длиннее 3 символов.
   Слова-генерики (кафе, бар, quán, nhà hàng, ร้าน…) не считаются. Безымянные не склеиваются.
4. **Радиус.** На экране параметров 100 / 200 / 500 / 1000 м (по умолчанию 200). Если мест меньше
   трёх, радиус расширяется шагами 100 → 200 → 300 → 500 → 1000 по уже загруженным данным, без нового
   запроса; предел — полнота данных (OSM-«ведро» 600 м даёт до 500 м, Foursquare — 1000 м). В
   выдаче над местами появляется пометка о расширении. Если Telegram передал точность
   геопозиции (`horizontal_accuracy`) хуже радиуса, поиск стартует с ближайшего шага не меньше
   неё. У точки, выбранной на карте, точности нет.
5. **Ранжирование.** Среди мест с рейтингом: 0.7·рейтинг/5 − 0.03 за каждые 100 м расстояния
   (штраф абсолютный и не зависит от выбранного радиуса); безымянные — после именованных.
   Если мест с нужным рейтингом меньше трёх, добираются лучшие из остальных (с пометкой).
   Расстояние в карточках округляется до 10 м.

### Хранение данных

- **FSM (Redis, ≤ 6 ч):** текущая и «домашняя» точка, радиус, точность геопозиции.
- **`user_lastloc:{id}` (≤ `LASTLOC_TTL_HOURS`):** последняя «моя» геопозиция — для inline на
  Desktop. **`user_prefs:{id}`:** радиус, порог рейтинга, категория.
- **`place:meta:*`:** название, координаты и адрес показанных мест — **только** из OSM/Geoapify;
  данные Foursquare и Mapbox не сохраняются, у них хранится лишь `place_id` в отметках
  (в старой базе очистка: `python -m bot.diag purge-meta [--apply]`).
- **Кэши (Redis, `OSM_CACHE_TTL` — сутки):** `places:v5:*` — результаты OSM-провайдеров (ключ — хеш ячейки
  ~100 м, радиуса-«ведра», языка, провайдера и категории); `region:v1:*` — названия региона точки из
  Geoapify reverse (ключ — хеш ячейки ~110 м, без привязки к пользователю); `geo:v2:*` — результаты
  геокодера Nominatim по адресу из текста (ключ — хеш запроса, языка, окрестности ~11 км и `limit`;
  значение — до 3 кандидатов: координаты и подпись).
- **Жалобы «закрыто»** — `place:closed:{place_id}`: id пользователя → вес жалобы, `CLOSED_TTL_DAYS`.
- Ответы Foursquare на сервере не кэшируются вообще.

## Монетизация и геймификация

**По умолчанию монетизация ВЫКЛЮЧЕНА** — после обновления никто не упрётся в paywall.
Админ управляет на лету командой `/money` (настройки в Redis, переживают перезапуск):
`/money` — статус, `/money on` / `/money off`, `/money free N` (бесплатных поисков в день),
`/money exempt off` — отключить безлимит админа, чтобы проверить paywall на себе.
Пока выключено: лимитов и paywall нет, `/buy` отвечает «сейчас бесплатно»; серия, рефералы и
отметки продолжают копиться.

**Тизер: платные данные — за Stars.** Рейтинги, число оценок и фото мест — Premium-поля
Foursquare, они стоят денег (кредиты). Поэтому два уровня:
• **с рейтингами и фото** — `FREE_SEARCHES_PER_DAY` поисков в день бесплатно (по умолчанию 1,
  +1 за каждый день серии, максимум `STREAK_BONUS_CAP`), дальше — бонусные поиски
  (рефералы, серия, отметки, пакеты за Stars) или Pro (потолок `PRO_DAILY_LIMIT`);
• **базовый** — имя, адрес, расстояние, категория, фото-заглушка и «народные» рейтинги 🥷;
  доступен всегда (потолок `BASE_DAILY_LIMIT` в день — защита инфраструктуры).
Списывается только поиск, сделавший обращение к API: ответы из кэша, пустые результаты и
ошибки бесплатны; если Foursquare не отдал платные поля (нет кредитов), бонусный поиск не
списывается. Когда лимит «с рейтингами» исчерпан, под выдачей появляется заметка и кнопка
«⭐ Рейтинги и фото», а фильтр рейтинга на экране параметров заменяется на «🔒 … открыть».
Новый день наступает по `QUOTA_UTC_OFFSET_HOURS`. `/money free N` меняет размер тизера на лету
(0 — без бесплатных поисков с рейтингами).

**Paywall-блок** (лимит базовых поисков) показывается только когда потолок `BASE_DAILY_LIMIT`
исчерпан, никогда до первого поиска. Товары за Telegram Stars (XTR): +20 поисков с рейтингами,
Pro на 7/30 дней, заморозка серии. Цены — `STARS_PRICE_*`.

**Серия.** День засчитывается за успешный поиск. Награды за 3/7/14/30 дней — бонусные
поиски. Заморозка спасает серию при одном пропущенном дне.

**Рефералы.** Ссылка `t.me/<bot>?start=ref_<id>` (в `/me` и на paywall). Оба получают
`REFERRAL_BONUS` поисков после ПЕРВОГО успешного поиска приглашённого. Уже искавшие
пользователи и самоприглашение не засчитываются; потолок `REFERRAL_MAX_REWARDED`.

**Платежи.** `pre_checkout_query` проверяет цену и владельца заказа, повторная доставка
`successful_payment` идемпотентна (`payment:{charge_id}`). Возврат: `/refund <charge_id>`
(админ); выданный товар автоматически не отзывается.

Метрики: `/stats` показывает покупки, Stars за день и показы paywall.

## Выдача: карточки с фото

Заголовок («✨ Топ-3 места рядом с вами») и под ним по сообщению-карточке на место: фото
(реальное — у платящих, если оно есть у Foursquare/OSM; иначе фирменная заглушка по типу
заведения), название, ⭐ рейтинг · 🚶 расстояние, категория и кнопки
🗺 Карта · 📤 Поделиться / 👍 · 👎 (счётчики и ✅ обновляются прямо на кнопках).
Telegram не умеет «карточки» из нескольких блоков с кнопками в одном сообщении, поэтому одна
карточка = одно фото-сообщение с подписью (лимит подписи — 1024 символа).

**Чтобы карточки не «плыли»:** название обрезается до 38 символов с «…», а полное уходит в
сворачиваемую цитату («под кат»); адрес, категория и полное название имеют свои пределы; из
внешних строк вычищаются bidi-символы, нулевая ширина и переводы строк, всё экранируется под
HTML. Проверено на 120–200-символьных названиях, слове без пробелов, HTML-инъекции, RTL, CJK
и составных эмодзи (`scripts/smoke.py`, максимальная подпись в тестах ≈ 500 символов).
Если Telegram не смог загрузить фото по ссылке — карточка уходит с заглушкой, а не пропадает.

## Вид выдачи: cards или compact

`cards` (по умолчанию) — заголовок и фото-карточки отдельными сообщениями. `compact` — всё в
одном сообщении: заголовок, затем по сворачиваемой цитате (`<blockquote expandable>`) на место
(видны имя, рейтинг · расстояние и категория, адрес — «под катом»), кнопки рядами под
сообщением (🗺 📤 👍 👎 🚫 на место). Переключает админ на лету: `/layout cards` / `/layout compact`.

## Источники данных, кэш и лицензии

- **Один запрос — один провайдер.** Места разных источников в одной выдаче не смешиваются:
  правила Foursquare запрещают серверный кэш и интеграцию с материалом под share-alike (ODbL,
  то есть OSM). Платный поиск идёт в Foursquare; если там меньше 3 мест, берётся базовый
  провайдер с большим числом мест (рейтинги в этом случае не показываются и не списываются).
- **Foursquare не кэшируется** (никакого хранения ответов на сервере): каждый платный и
  FSQ-поиск — живой вызов. В Redis хранятся только `place_id` в отметках 👍/👎.
- **Geoapify / Overpass (OSM)** кэшируются по ячейке ~100 м (`OSM_CACHE_TTL`, сутки): запрос
  идёт из центра ячейки с запасом радиуса («вёдра» 600 и 1100 м), расстояния считаются от
  точки пользователя. Категория фильтруется на стороне провайдера и входит в ключ кэша.
- **Порядок базового поиска** — `BASE_PROVIDERS` (по умолчанию `geoapify,fsq,overpass`):
  первый провайдер, давший ≥ 3 места, иначе тот, у кого мест больше. Без `GEOAPIFY_API_KEY`
  Geoapify пропускается.
- **Атрибуция** добавляется в выдачу и inline по провайдеру: «Powered by Geoapify · ©
  OpenStreetMap contributors», «© OpenStreetMap contributors» или «Powered by Foursquare».
- Foursquare — всегда живой запрос на радиус 1000 м (`limit=50`, `sort=DISTANCE`; если API
  отвергнет параметр — отключается сам; то же для поля `date_closed`). Меньшие радиусы и
  авто-расширение считаются в памяти по этому же ответу. Серверный фильтр категорий FSQ: `python -m bot.diag cats [lat lon]` выводит
  реальные категории заведений (id и название) — по ним подбираются id для cafe/bar/restaurant.

## Диагностика внешних сервисов

`/diag` (админ) или `docker compose exec telegram-bot python -m bot.diag` проверяют Redis,
Telegram, Foursquare, **каждое зеркало Overpass** (слоты `/status` + реальный запрос) и
Nominatim, с временем ответа и причиной ошибки. `/diag premium` проверяет и платные поля
Foursquare (расходует 1 Premium-вызов).

Остальные команды работают только из консоли (`docker compose exec telegram-bot python -m bot.diag …`):
`raw [lat lon [radius]]` — сырой ответ Foursquare (координаты, расстояния, адрес, `closed=`),
`cats [lat lon]` — категории заведений рядом, `dish <город:блюдо | слово> [lat lon]` — что найдёт
«Найти блюдо» (совпадения по радиусам и написаниям), `purge-meta [--apply]` — чистка `place:meta:*`
от мест не из OSM/Geoapify (без `--apply` только считает).

**Overpass.** Серверы пробуются строго по очереди (`OVERPASS_URL`, через запятую); не ответивший
уходит на паузу на 90 с, поэтому один сбой не добавляет по 10 секунд к каждому поиску; если на
паузе все — Overpass пропускается мгновенно. Для добавления своего зеркала допишите его в
`OVERPASS_URL` и проверьте `/diag`. Правила публичных серверов: кэшировать, не гонять параллельные
запросы; для коммерческого трафика вики OSM рекомендует свой или платный Overpass. Данные ©
участники OpenStreetMap (ODbL): при выдаче с OSM-данными бот добавляет эту строку.

## Inline-режим

`@бот` в любом чате показывает **3 ближайших** места (по расстоянию). Выдача inline — всегда
базовая (на каждый символ идёт запрос — тратить Premium-кредиты нельзя); поиск ограничен по
времени (если не успел — «⏳ Ищу места…», а кэш наполняется в фоне).

Точка поиска (по порядку): геопозиция inline-запроса → последняя «моя» геопозиция, присланная
боту в диалоге (`user_lastloc`, живёт `LASTLOC_TTL_HOURS` = 6 ч) → подсказка «отправьте боту
геопозицию». Координаты, ссылка Google Maps или адрес в тексте запроса задают точку явно.

Токены в запросе (порядок любой):

- радиус: `200м`, `1км`, `1.5km`, `r1000` — значение «прилипает» вверх к 100 / 200 / 500 / 1000 м
  (иначе кэш по точке дробится; потолок `INLINE_MAX_RADIUS` = 1000); без токена — радиус из
  настроек пользователя (`user_prefs`, только допустимые значения), иначе `INLINE_DEFAULT_RADIUS`
  (200);
- слово `рядом` / `near` — «вокруг моей точки», ни на что не влияет (его можно не писать);
- категория: `кафе`, `бар`, `ресторан` (и `cafe`, `pub`, `restaurant`…);
- остальное — фильтр по названию или адрес. Пример: `@бот кафе 1км`.

Кнопка над выдачей показывает текущий радиус и ведёт в бота (`/start inline_help`) за справкой
со списком команд. Внутри inline выбрать точку на карте нельзя: работают геопозиция Telegram,
координаты или ссылка Google Maps в тексте и последняя точка, присланная боту.

Настройка в @BotFather (писать именно ему, не боту): `/setinline` — включить, затем отдельным
сообщением текст подсказки в поле ввода (например `500м · кафе · адрес · координаты`) — и
`/setinlinegeo` (Enable — иначе Telegram не передаёт геопозицию в inline-запросах). По имеющимся
сведениям, геопозицию inline передают только мобильные клиенты после разрешения пользователя;
Desktop — нет, поэтому нужен фолбэк на последнюю присланную боту точку.

## Сайт и автоматизация

Сайт (лендинг RU/EN, условия, конфиденциальность, гиды по городам) **собирается из репозитория
автоматически** и выкладывается на GitHub Pages; руками ничего не публикуется.

- **Источники:** тексты — `site/content/{ru,en}.json` (структуры RU и EN должны совпадать, это
  проверяется), настройки — `site/config.json` (имя бота, адрес сайта, ссылки на канал/чат/
  поддержку, `money_enabled`), текст раздела «Покупки» — из локалей бота (`terms_text`), гиды —
  из `bot/data/specialties.json`. **В гиды попадают только блюда `verified: true` со ссылками
  на источники**; пока таких нет, гидов и рекламы «Что попробовать» на сайте нет.
- **Сборка:** `python -m scripts.build_site --out _site --check` (внутренние ссылки, title/lang,
  плейсхолдеры). Ссылки между страницами относительные: сайт живёт под `/<репозиторий>/`.
- **Выкладка:** `.github/workflows/pages.yml` — при изменении сайта, словаря или локалей на main.
  Один раз включить: Settings → Pages → Build and deployment → Source: **GitHub Actions**.
  Адрес по умолчанию — `https://<владелец>.github.io/<репозиторий>/`; пропишите его в
  `site/config.json` (`site_url`) и в `.env` бота (`SITE_URL`).
- **Бот и сайт:** `/terms` и `/paysupport` добавляют ссылки на страницы сайта (на языке пользователя,
  zh → en) и, если задан `SUPPORT_URL`, на поддержку. Кнопка сайта ведёт в `t.me/<бот>?start=site_<язык>`;
  переходы считаются в статистике (`site_ru`, `site_guide_en`, …).
- **Профиль бота — тоже из репозитория:** `bot/data/bot_profile.json` (команды и описания на
  ru/en/zh) применяется при каждом старте (`setMyCommands`, `setMyDescription`,
  `setMyShortDescription`), без ручной работы в @BotFather. Остаются только настройки, у которых нет метода
  Bot API: режим inline и подсказка в его поле (`/setinline`).
- **Зависимости обновляются сами:** `.github/dependabot.yml` (pip и GitHub Actions).
- Политика конфиденциальности — черновик владельца проекта, не юридическая консультация; при
  изменении хранимых данных (раздел «Хранение данных») её нужно править вместе с кодом.

## ИИ-конвейеры (OpenRouter, бесплатные модели)

Рутина вынесена в GitHub Actions; модель только готовит текст, решение остаётся за человеком там,
где ошибка дорого стоит. Клиент — `scripts/ai/llm.py` (OpenRouter, цепочка бесплатных моделей `:free`,
запасная модель при сбое, остановка при суточном лимите).

| Конвейер | Когда запускается | Что делает | Кто решает |
|---|---|---|---|
| `announce.yml` | выпуск релиза (Releases → Publish) или вручную | пишет объявление RU+EN по заметкам релиза и темам коммитов | **по умолчанию подтверждение**: черновик приходит админу в бот с кнопками «✅ Опубликовать» / «❌ Отклонить»; режим `auto` — сразу в канал |
| `dictionary.yml` | раз в неделю (пн) или вручную | добавляет в словарь следующий город из `bot/data/city_backlog.json` (`mode=city`) либо `venue_tokens` (`mode=tokens`); **каждую ссылку скачивает** и оставляет только открывшиеся, где встречается название блюда (нужно ≥ 2 сайтов) | pull request с `verified: false`; `true` ставит человек |
| `translate.yml` | изменение `bot/locales/*.json` или вручную (`langs=vi,th`) | переводит недостающие строки; проверяет плейсхолдеры `{x}`, HTML-теги, длину | pull request; новый язык подключается в боте отдельно |

**Переключатель объявлений.** Переменная репозитория `ANNOUNCE_MODE`: `approval` (по умолчанию) или
`auto`; при ручном запуске — поле `mode`. Для `approval` у бота должны быть `ADMIN_ID`, а у бота в `.env` —
`CHANNEL_ID`; для публикации бот должен быть администратором канала с правом писать посты.

**Настройка один раз:** Settings → Secrets and variables → Actions:
секреты `OPENROUTER_API_KEY` и `BOT_TOKEN`; переменные `ADMIN_ID`, `CHANNEL_ID` (`@username` канала),
`ANNOUNCE_MODE`, при необходимости `OPENROUTER_MODELS` (id моделей через запятую; если пусто, берутся
бесплатные из каталога OpenRouter). Для PR: Settings → Actions → General → «Allow GitHub Actions to
create and approve pull requests». Pull request, созданный от `GITHUB_TOKEN`, сам не запускает CI —
откройте его и нажмите Re-run (или используйте PAT).

**Ограничения бесплатного тарифа** (по документации OpenRouter на момент написания): 20 запросов в
минуту и 50 в сутки на аккаунт (1000 после пополнения от $10), неудачные запросы тоже считаются,
идентификаторы `:free`-моделей меняются, а часть бесплатных endpoint'ов может логировать запросы.
Поэтому конвейеры: делают минимум запросов (одна попытка на модель, одна повторная при невалидном
ответе), при исчерпании лимита завершаются без ошибки и ждут следующего запуска, и отправляют
модели **только содержимое репозитория** (заметки релиза, словарь, строки локалей) — никаких данных
пользователей. Модель без выхода в интернет может выдумывать ссылки: поэтому источники словаря
проверяются скачиванием, а не принимаются на веру.

Защита workflow: данные из событий GitHub попадают в скрипты только через `env`, а не в `run:`
(тест `test_ai` падает при `${{ … }}` внутри `run:`); секреты и токены не пишутся в логи и ошибки.

## Закрытые места

Foursquare отдаёт `date_closed` (закрыто навсегда) — такие места отбрасываются сами, до выбора
провайдера. У OSM/Geoapify такого признака нет, поэтому под местом есть кнопка **«🚫 Закрыто»**:
одна жалоба на человека и место; после `CLOSED_REPORTS_THRESHOLD` (2) жалоб разных людей место
скрывается из выдачи на `CLOSED_TTL_DAYS` (60) дней, потом возвращается (временно закрытое
откроется, постоянно закрытое получит жалобы заново). У админа достаточно одной жалобы. Жалоба
засчитывается как отметка в награде (`VOTE_REWARD_*`).

## Что попробовать здесь

Бесплатная карточка по кнопке «🍜 Что попробовать здесь» под выдачей: блюда и напитки города,
в радиус которого попала точка поиска (без внешних запросов и квоты). Данные —
`bot/data/specialties.json`: города (центр + радиус) и блюда с названием на местном языке,
описанием, подсказкой «как есть», вариантами написания для поиска (`search_tokens`) и ссылками
`sources`. Блюда с `verified: false` пользователям не показываются; `verified: true` допустим
только со ссылкой в `sources`. Для просмотра черновика — `SPECIALTIES_SHOW_UNVERIFIED=true`.

```bash
BOT_TOKEN=x FSQ_API_KEY=x python -m scripts.test_specialties путь/к/словарю.json   # проверка схемы
BOT_TOKEN=x FSQ_API_KEY=x python -m scripts.merge_specialties review.json [--write] # влить ответ ИИ
```

Слияние никогда не меняет `verified` и не удаляет блюда: `removals` только перечисляются.
Необязательные поля: `title_en` / `short_desc_en` / `how_to_eat_en` (без них en/zh показывают русский
текст) и `venue_tokens` (см. «Найти блюдо»).

## Найти блюдо

Под карточкой «Что попробовать здесь» у каждого блюда есть кнопка «🔎 …»: она запускает поиск
заведений с этим блюдом вокруг текущей точки **в радиусе, выбранном пользователем**; если таких мест
меньше трёх, радиус расширяется (100 → 200 → 300 → 500 → 1000, но не дальше полноты данных
провайдера) и над выдачей показывается пометка. То же работает по тексту: если в чате написать
название блюда своего города (`pho bo`, `Bún chả`, `cơm tấm`), бот ищет его вокруг текущей точки; в
inline `@бот pho bo` фильтрует ближайшие места так же, без учёта диакритики (Phở = Pho).

Как это устроено и чем ограничено:

- Поиск идёт по **названию и категории** заведения, меню мы не знаем — в выдаче так и сказано.
  Критерий — слова `venue_tokens` блюда (то, что встречается в названиях заведений: «pho», а не
  «pho bo»); если поля нет, берутся `search_tokens` — полнота при этом заметно ниже. Сейчас поле заполнено
  у 55 из 56 блюд (кофе с яйцом в Ханое оставлен без него: по названию заведения не опознать); слова
  подобраны по общим знаниям и ещё не сверены с живыми данными — проверьте `bot.diag dish` на своих точках. Латиница
  сравнивается целыми словами («pho» не найдёт «Phong Lan»), тайский — подстрокой.
- Это базовый слой: данные текущего провайдера (Geoapify/Overpass из кэша, FSQ живой), без платных
  рейтингов и без отдельных запросов под блюдо. Квота как у базового поиска, настройки
  пользователя (радиус, рейтинг, категория) поиск блюда не меняет.
- Закрытые места, «битые пины», дубли и чужие регионы чистятся так же, как в обычной выдаче.
- Набор данных провайдера обрезан по лимиту (Geoapify — 100 ближайших мест на «ведро»): в плотном
  районе дальние совпадения могут не попасть. Проверить на живых данных:
  `python -m bot.diag dish hanoi:pho_bo_hanoi` (признак «НАБОР ОБРЕЗАН», совпадения по радиусам и по
  каждому написанию). Если обрезка частая — понадобится целевой запрос провайдеру по названию.

## Категории

На экране параметров — ряд «Всё / Кафе / Рестораны / Бары» (запоминается в `user_prefs`).
Для Geoapify и Overpass категория фильтруется на стороне провайдера и входит в ключ кэша; у
Foursquare фильтр локальный — по названию категории (ru/en/zh/vi/th), поэтому он не тратит запросы.
Места с неопознанной категорией (пекарни без метки, отели и т. п.) показываются только в режиме «Всё».

## Произвольная точка поиска

Искать можно не только «рядом со мной». Где задать точку: 📎 → «Геопозиция» → выбрать любое
место на карте; или написать адрес/название места; или прислать координаты / ссылку Google Maps
(в т.ч. короткую `maps.app.goo.gl`); или переслать место (venue). Кнопка «🗺 Другая точка» на
экране параметров подсказывает варианты, «📍 Рядом со мной» возвращает назад.
«Домашняя» геопозиция при выборе временной точки не перезаписывается; в выдаче и на экране
параметров видно, где идёт поиск. Адреса ищутся через OpenStreetMap Nominatim (текст запроса
уходит на их сервер; `GEOCODER_ENABLED=false` отключает). Полноценный выбор точки внутри
Telegram-интерфейса без «скрепки» возможен только через Mini App — отдельный этап.

## Отметки «был здесь»

👍/👎 под карточкой. Один голос на пользователя и место (можно передумать). Для мест без
рейтинга провайдера считается «народный» рейтинг со сглаживанием: `5·(👍+1)/(👍+👎+2)`,
в выдаче он помечен 🥷. Чтобы дотянуть место до порога «4.0+», нужно не меньше трёх
одобрительных отметок подряд. Награда: каждые `VOTE_REWARD_EVERY` новых отметок — +1 бонусный
поиск (не больше `VOTE_REWARD_DAILY_CAP` в день).

## Ссылки «на карту» и «поделиться»

В Google Maps URL нет радиуса или границ, а `/@lat,lon,zoom` задаёт лишь центр карты: если по
тексту ничего не нашлось рядом, Google ищет по всему миру и подсовывает тёзку (например, в
Китае). Поэтому у места с названием ссылка ищет по тексту «название, адрес, город» (город — из
адреса или поля `locality` провайдера) и центрируется на координатах; у безымянных мест и у
названий с иероглифами (главный источник тёзок) ссылка идёт по координатам — точный пин без
карточки Google. Place ID Google у нас нет. 📤 открывает выбор получателя с названием, адресом,
ссылкой на карту и реферальной ссылкой на бота.

## Метрики качества

`/stats` (админ) показывает: долю поисков с тремя местами, без рейтинга, с «добором», из кэша,
число обращений к API (прокси стоимости), сбои Foursquare, использование OSM-фолбэка, число
случаев «недоступно», долю поисков с рейтингами и среднее время ответа. Одинаковые параллельные запросы к OSM-провайдерам с
промахом кэша объединяются (один вызов API); Foursquare всегда живой, без объединения.

## Известные ограничения

- Категории Foursquare: новый API принимает только 24-символьные ID (числовые вроде 13065 дают HTTP 400). Используется родитель «Dining and Drinking»; если и он отвергнут — запрос без фильтра и отбор по названию категории.
- Публичные зеркала Overpass нестабильны (часть недоступна с некоторых VPS): проверяйте `/diag`;
  для коммерческого трафика нужен свой или платный Overpass.
- Адреса Foursquare в провинциях Вьетнама могут быть записаны по старому административному
  делению (до реформы 2025); сверка региона лишь переставляет такие места в конец выдачи.
- Места из Foursquare и OSM — разные `place_id`: отметки и жалобы не переносятся между ними.
- `rating`/`stats` — расширенные поля Foursquare; их доступность зависит от тарифа ключа.
